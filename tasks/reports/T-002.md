## 6. Decisions made
- **D1 diff timing.** `runner.rs` `DECISION(T-002)`: changed paths and `git diff --stat` are taken after the
  agent and before the checks, so build artefacts left by checks are not counted as the agent's edits.
  Checks' leftovers are committed with the same task, so they do not appear in the next task's diff either.
- **D2 pass rule.** `runner.rs` `DECISION(T-002)`: a task passes only if the agent `Completed` **and** every
  check passed. Checks always run, even after a timeout or failure.
- **D3 `file_absent`.** `config.rs` `DECISION(T-002)`: means "this path must not exist".
- **D4 defaults.** `config.rs` `DECISION(T-002)`: `timeout_secs` defaults to 1800 (task) and 600 (check), the
  values in the task file's example.
- **D5 spawn failure.** A `command` agent program that cannot start returns `EvalError::Spawn` and aborts the
  batch (misconfiguration, not agent behaviour). Results already written stay on disk.
- **D6 relative `source`.** `runner.rs` `DECISION(T-002)`: a relative local path in `repos.toml` is resolved
  against the eval directory.
- **D7 arms.** Arm files are committed in the working copy before task 1, so they are not task 1's changes.
  `from` may be a file or a folder (copied recursively; symlinks are rejected).
- **D8 report grouping.** One table per chain × arm × **agent**. Chain total "pass" means every recorded task of
  the run passed. A total sums the metrics that are present; a metric missing from every task is `–`.
- **D9 validation extras** beyond the spec: names must be `[A-Za-z0-9_-]` without `__`, `chain.id` must equal the
  folder name, `arm.name` the file name, `base_commit` must be 7+ hex digits (no moving refs), paths from files
  must be relative without `..`, ids and check names unique, repo must exist, agent files are parsed too.
- **D10 git environment.** Every git call sets `core.autocrlf=false`, `commit.gpgsign=false`,
  `core.quotepath=false`, `GIT_TERMINAL_PROMPT=0` and the fixed identity `inklore-eval <eval@inklore.invalid>`.
  Commits use `--allow-empty --no-verify`.
- **D11 paths.** Batch id `batch-<unix-seconds>` (suffix `-N` on collision); agent logs go to
  `results/<batch>/logs/<run-id>/<task-id>/`; working copies stay in `eval/.work/` after a run.
- **D12 test helpers.** The `command` tests re-run the test binary with `--ignored --exact <helper>`; the helper
  tests are `#[ignore]`d so a plain `cargo test` shows them as ignored. A helper prints an empty line first because
  libtest has already written `test … ... ` without a newline, then the JSON line, then exits before libtest can
  print its summary. Integration test files carry `#![allow(clippy::unwrap_used, …)]` because clippy's
  `allow-unwrap-in-tests` does not cover helper functions in `tests/`.
- No `tracing` dependency: the library does not log; the runner reports progress through a callback and the
  binary prints it.

## 9. Known issues and leftovers
- Windows: a grandchild that has **already been orphaned** (its parent exited before the timeout) cannot be
  found by `taskkill /T`, so it is not killed. Output capture then stops after a 2 s grace period instead of
  hanging. Same limitation on Unix for processes that leave the group (`setsid`).

  may be wanted for very chatty agents.

## 11. Task-specific answers
1. **Killing the process tree.** Unix: the child is started in its own process group
   (`CommandExt::process_group(0)`) and on timeout `nix::sys::signal::killpg(pid, SIGKILL)` kills the group,
   then `child.kill()` and `wait()` reap it. Windows: `taskkill /T /F /PID <pid>` is run as an executable, then
   `child.kill()` and `wait()`. Verified on Windows with a test where the child starts a grandchild that would
   write a file after 4 s: with the kill the file never appears, with the `taskkill` call disabled the test fails.
   The Unix path compiles and lints on `x86_64-unknown-linux-gnu` but was not run here; CI will run it.
   Limitations: processes that already left the tree (orphaned or `setsid`) are not found; after a *normal*
   exit nothing is killed (a late `killpg` could hit a reused pid), so a daemon the agent leaves behind keeps
   running; output readers give up after 2 s in that case.
2. **Sample.** Produced by the real binary against a throwaway repository with a scripted agent, two runs of a

3. **Awkward in the formats (for T-003).**
   - Metrics come only from one stdout JSON line, and real agent CLIs (Claude Code, Codex) report tokens and
     cost in their own JSON output, so T-003 will want a per-agent parser (or a `metrics_from` setting) instead
     of requiring the program to print the harness's own field names.
   - There is no way to say that a check is about the agent's *final diff* (rule checkers) or about
     out-of-scope edits; `changed_paths` is recorded, but the "intended scope" per task has no place in
     `chain.toml` yet (a `scope = ["internal/modules/orders/**"]` list would fit).
   - `command` checks run with the machine's `PATH` and tools: nothing pins the Go or Node version a chain
     needs. A `requires` note or an environment block per chain would help reproducibility.
   - A chain's `base_commit` must be written by hand; a `validate --resolve` that checks the commit exists in the
     repo (without running anything) would catch typos earlier than the first run.
   - The `scripted` TOML needs one `[[tasks.<id>]]` table per action; fine for tests, noisy for long scripts.
   - Arms can only copy files; the "pull" and "push" arms will also need to install an MCP server config and
     hooks, probably as a setup command run in the working copy.
   - Windows: a bare program name such as `claude` that is a `.cmd` shim is not found without a shell;
     T-003 should resolve the real executable (or use `cmd /c` explicitly in the agent config).
