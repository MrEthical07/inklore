## R1 — Bug: two runs in the same second share a working copy

`Run::execute` builds the run id as `<chain>__<arm>__<agent>__r<N>__<unix-seconds>`, and
`prepare_working_copy` uses `eval/.work/<run-id>`. Two batches that start the same run within one second
get the same folder, and the second `git clone` fails with *destination path already exists*. The test
above runs two batches back to back: on Windows it was slow enough to cross a second boundary, on Linux it
is not. The batch directory already handles collisions; run directories do not. (The format came from the
task file, so the spec was wrong, not the implementation.)

Fix:
1. Replace the trailing Unix seconds in the run id with the **batch id**:
   `<chain>__<arm>__<agent>__r<N>__<batch-id>`. Run ids are then unique by construction, because batch
   directories already are.
2. In `prepare_working_copy`, refuse to reuse a folder: if `eval/.work/<run-id>` already exists, return
   an error instead of cloning into it.
3. Add a regression test that calls `run_batch` twice in a row with identical options, with no delay, and
   asserts both succeed and their `run_id`s differ.
4. Update `eval/README.md` and the report wherever the run-id format is described.

The reviewer applied steps 1–2 to a scratch copy: all `inklore-eval` tests then passed three runs in a row
on Linux.
